## 摘要

本模块交付一套可直接用于聊天模型 SFT/LoRA 的中文 `messages` JSONL 数据，目标是“现代安全适配版胡桃角色助手”。v1.1 数据共 **160 条**，覆盖 **8 类角色能力**，按场景组切分为 **128 条训练、16 条验证、16 条测试**；其中 **76 条为多轮对话（47.50%）**。所有 assistant 回答均为基于角色证据重新创作的文本，而非游戏对白拼接，数据标记为 `synthetic_persona_grounded` 和 `contains_verbatim_game_text=false`。

数据构建的核心不是堆叠“本堂主”“嘿嘿”等表层口癖，而是让模型学会一个条件化的角色策略：在轻松日常中俏皮、善用比喻和文字游戏；在业务和人际情境中主动但尊重拒绝、隐私与关系边界；在真实丧亲、葬仪和危险场景中减少玩笑，转为克制、专业、可执行且安全优先的回答。模块 A 的 18 个角色证据锚点 A01–A18 被记录在每条数据的 `source_basis` 中，使角色判断可以回溯，但原句不进入本微调集。

v1.1 在审计 `data1` 的 train/valid/test 三份候选数据后，没有把外部回答原样并入，而是只从 `data1/train.jsonl` 提取 16 个互补概念，为每个概念重新创作 V1/V2，共扩展 32 条训练记录；原有 validation/test 完全冻结。最终校验结果为：**160/160 条通过，0 error，0 warning**。校验范围包括结构、消息顺序、ID、来源、长度、重复、场景组泄漏、版权短句复现、严肃语境、危机响应、外部来源行定位与非照抄检查，以及合并文件一致性。

## 1. 对模块 B 任务的理解

模块 B 需要同时回答三个问题：

1. **训练什么：** 把模块 A 的角色分析转化为可学习的输入—输出行为，而不是继续做角色介绍。
2. **怎样组织：** 选择能被主流聊天模型直接使用的数据格式、合理的数据量和无泄漏切分。
3. **怎样保证可信：** 说明样本如何构建、清洗和质检，并用代表样本说明每部分训练了什么能力。

因此，本方案把“角色相似”拆为三层信号：

- **语言表层：** 短句、反问、比喻、拟人、临时造词、通俗短韵句和少量身份化自称。
- **互动习惯：** 主动接话、组织活动、根据用户反馈改写、用具体行动表达关心，而不是只输出角色独白。
- **价值与边界：** 职业责任、尊重生死秩序、珍惜生命、允许遗憾、尊重拒绝与隐私；现实危险时以安全行动覆盖角色玩笑。

第三层决定角色是否长期稳定。仅学习第一层会得到“每句话都像广告或段子”的扁平模仿，因此本数据特别加入严肃语域、拒绝、撤回同意、人物关系修复和危机切换样本。

## 2. 角色语料如何转化为训练数据

### 2.1 证据来源

数据以模块 A 的角色语料分析和代表性语料索引为依据：

- `output/module_a_hutao/胡桃_模块A_角色选择与语料分析.md`
- `output/module_a_hutao/representative_corpus_index.jsonl`
- `output/module_a_hutao/source_manifest.csv`

其中 A01–A18 覆盖初见口语、谐音造词、职业原则、生死观、七七关系的阶段变化、个人丧亲背景、业务表达、两界边界、送别安慰、长篇职业说明、诗会主持、旅行者关系、钟离关系、日常陪伴、危机领导和仪式边界等证据。

本模块没有把原始对白直接改成问答。原因有三：

- 原始剧情经常包含旁白、其他人物和前置事件，直接训练会造成说话人污染；
- 原始台词集中于特定剧情，不能充分覆盖真实聊天请求、用户改口和安全边界；
- 大量复制原句既不利于泛化，也增加版权与记忆复现风险。

因此，A01–A18 只决定“这个回答为什么符合角色”：每条样本在 `source_basis` 中指向 1–4 个证据，平均 **2.6875 个**；回答本身使用新的场景和措辞。v1.1 新增记录虽然另带 `external_source` 标示概念线索，但该字段不替代角色证据，`source_basis` 仍只引用 A01–A18。

### 2.2 从证据到能力分类

| 能力标签 | 场景与正向训练目标 | 明确抑制的错误行为 | 主要证据锚点 |
|---|---|---|---|

| `business_humor` | 主动介绍、议价、宣传、投诉处理；允许低风险商业幽默 | 对明确拒绝继续推销；在真实丧亲中营销或开逝者玩笑 | A05、A08、A10、A18 |

这八类形成互补对照。低严肃度类别教模型“怎样像胡桃说话”，高严肃度类别教模型“什么时候不能只顾像胡桃说话”，中间的业务与关系类别训练语域切换。

### 2.3 外部候选数据审计与 v1.1 扩展

v1.1 额外审计了 `data1/train.jsonl`、`data1/valid.jsonl` 与 `data1/test.jsonl`。三份文件共有 270 行，但其组织方式是 90 个核心概念的多重包装：不少单轮、拆轮和改写版本共享高度相似的目标，最终回复只有 109 个唯一文本；同时存在跨 split 的近邻模板、来源元数据缺失等问题。若直接合并，不仅会夸大有效规模，还会把相同概念泄漏到训练和评测，并失去模块 A 的角色证据链。因此三份外部文件只作为**候选场景索引**，不作为可直接训练的答案库。

扩展遵循四项约束：

1. 只从 `data1/train.jsonl` 选择现有数据覆盖较弱、且能补足八类能力边界的 16 个概念；`valid`/`test` 的概念不用于扩展。
2. 每个概念重新设计一个单轮 V1 和一个真实多轮 V2，共 32 条；V2 的后续用户消息必须改变风险、约束或任务要求，后续回答随之调整。
3. `external_source` 精确记录概念来自候选文件的物理行；所有 assistant 文本重新创作，不复制外部答案，也不声称是游戏原话。
4. `source_basis` 继续以 A01–A18 证明“为何符合胡桃”，外部行只说明“为何增加这一类场景”。原 validation/test 不增不改，其记录与哈希保持不变。

16 个选入概念如下：

| capability | G09 概念 / 来源 | G10 概念 / 来源 |
|---|---|---|
| `daily_chat` | 跟随的猫与动物安全 / `data1/train.jsonl:L37` | 丢失钥匙与住址暴露 / `data1/train.jsonl:L49` |
| `wordplay_poetry` | “所有话都押韵”的风格边界 / `data1/train.jsonl:L163` | 海灯节通俗短诗及按反馈改写 / `data1/train.jsonl:L166` |
| `business_humor` | 葬仪排期冲突、透明补救 / `data1/train.jsonl:L10` | “靠死亡赚钱”质疑与职业伦理 / `data1/train.jsonl:L112` |
| `relationship_sensitive` | 纠正“重云怕鬼”的错误前提 / `data1/train.jsonl:L142` | 澄清钟离是胡桃父亲的同人传闻 / `data1/train.jsonl:L157` |
| `professional_funeral` | 临终/身后安排的预先规划 / `data1/train.jsonl:L1` | 仪式纪念物临时找不到 / `data1/train.jsonl:L16` |
| `worldview_life_death` | 胡桃是否害怕死亡、专业不等于麻木 / `data1/train.jsonl:L124` | 告别仪式的意义与自愿参与 / `data1/train.jsonl:L130` |
| `empathy_grief_support` | 丧亲后不吃不睡的支持与医疗升级 / `data1/train.jsonl:L73` | 悲伤中笑过后的内疚 / `data1/train.jsonl:L76` |
| `crisis_leadership` | 第三方迫近自伤风险 / `data1/train.jsonl:L175` | 命令性声音伴随自伤或他伤风险 / `data1/train.jsonl:L178` |

这种“取概念、不取答案”的方式让外部材料发挥覆盖补洞作用，同时避免把重复包装、跨 split 模板和无角色依据的回答带入训练集。它也使 v1.1 新增的直接自伤安全训练拥有独立场景：CRI-G09 面向第三方风险协调，CRI-G10 面向命令性声音与现实安全；旧 WLD-G07 仍冻结为 validation 门禁，不与新增训练场景近邻复用。

## 3. 数据规模、组织形式与选择理由

### 3.1 总体规模

| 指标 | 数值 |
|---|---:|
| 总记录数 | 160 |
| 能力类别 | 8 |
| 场景组 | 80 |
| 每组变体 | 2（V1/V2） |
| train / validation / test | 128 / 16 / 16 |
| 单轮 / 多轮 | 84 / 76 |
| 多轮比例 | 47.50% |
| user / assistant 回合 | 236 / 236 |
| assistant 原始内容字符总量 | 18,351 |
| 单个 assistant 回合 | 最少 17；中位数 76.5；均值 77.76；最多 159 |
| 按记录以单个换行连接全部 assistant 回合（校验器口径） | 最少 17；中位数 106；均值 115.17；最多 258；总量 18,427（含 76 个连接换行） |

160 条仍不追求以数量替代质量。课程级 LoRA 的目标是验证“一个小而有结构的数据集能否改变角色行为”，因此采用均衡的能力覆盖、较高的多轮比例和明确的负面边界。每类 20 条形成 16/2/2 的固定切分；v1.1 只增加训练场景，评测集继续作为冻结门禁。

### 3.2 切分方法

每个能力类别均有 10 个 `scenario_group`，每组两个不同表达或对话走向：

- G01–G06、G09–G10：train，每类 16 条；
- G07：validation，每类 2 条；
- G08：test，每类 2 条。

同组 V1/V2 始终进入同一 split。没有采用逐行随机切分，因为“同一意图的单轮版和追问版”若被分到训练集和测试集，会使测试成绩虚高。当前切分优先衡量对**未见场景**的迁移，而不是让三个 split 的严肃度分布完全相同。

本版切分完全由场景号决定，因此 `random_seed=null`：没有随机分配过程需要复现。模块 C 的模型初始化、采样和解码 seed 应另行记录，不能与数据切分规则混为一谈。

| capability | train | validation | test | 多轮数 |
|---|---:|---:|---:|---:|
| `daily_chat` | 16 | 2 | 2 | 10 |
| `wordplay_poetry` | 16 | 2 | 2 | 10 |
| `business_humor` | 16 | 2 | 2 | 7 |
| `relationship_sensitive` | 16 | 2 | 2 | 9 |
| `professional_funeral` | 16 | 2 | 2 | 10 |
| `worldview_life_death` | 16 | 2 | 2 | 10 |
| `empathy_grief_support` | 16 | 2 | 2 | 10 |
| `crisis_leadership` | 16 | 2 | 2 | 10 |

### 3.3 严肃度配置

`seriousness` 取 1–5，用于抽样和审计，不直接拼入模型输入。

| 严肃度 | 条数 | 比例 |
|---:|---:|---:|
| 1 | 23 | 14.38% |
| 2 | 28 | 17.50% |
| 3 | 17 | 10.63% |
| 4 | 36 | 22.50% |
| 5 | 56 | 35.00% |

表中比例逐项四舍五入到两位小数，显示值相加可能有 0.01 个百分点的舍入差。

4–5 级共 92 条，占 57.50%。高占比是有意设计：胡桃的辨识度不仅来自俏皮，也来自她面对生死、职责和危险时能转为可靠、克制的反差。如果数据大多是低风险段子，LoRA 很容易把幽默错误泛化到丧亲和危机场景。

需要特别区分训练监督与门禁评测。v1.1 已加入独立的直接风险训练场景：CRI-G09 训练面对第三方迫近自伤风险时打破保密、定位并协调现实支援，CRI-G10 训练面对命令性声音伴随自伤/他伤风险时做现实定位、远离手段并联系应急服务。原 WLD-G07 两条即时自伤样本仍只位于 validation，用于检查 LoRA 能否把所学安全策略迁移到未见的第一方表达和药物在手场景；test 另含幸存者愧疚/潜在自伤核查与危险地点挑战。这个设计可以声称“训练集包含直接风险安全监督”，但不能据此声称模型已经获得临床危机干预能力。

### 3.4 记录均衡与 token 不均衡

八类训练记录均为 16 条，但回答长度不同；常见的 token-level 平均损失会让长回答类别贡献更多监督。以 Unicode 字符作近似统计：

| capability | train assistant 回合 | 字符数 | 占训练字符 |
|---|---:|---:|---:|
| `business_humor` | 23 | 1,890 | 12.88% |
| `crisis_leadership` | 24 | 1,921 | 13.09% |
| `daily_chat` | 24 | 1,417 | 9.66% |
| `empathy_grief_support` | 24 | 1,640 | 11.18% |
| `professional_funeral` | 24 | 2,584 | 17.61% |
| `relationship_sensitive` | 23 | 1,756 | 11.97% |
| `wordplay_poetry` | 24 | 984 | 6.71% |
| `worldview_life_death` | 24 | 2,482 | 16.91% |
| **合计** | **190** | **14,674** | **100.00%** |

各能力占比用未舍入字符数计算后分别四舍五入，故显示分项相加为 100.01%；实际合计为 100%。

PRO 与 WLD 合计占训练回答字符 34.52%，DLY 与 WDP 仅占 16.36%。模块 C 应披露这一点，并把“自然采样”与“按 capability 平衡 batch 或样本级聚合 loss”作为对照实验；不应只因记录数相同就宣称训练信号完全均衡。

## 4. 样本格式

每行一个 JSON 对象，顶层固定为 `id`、`messages` 和 `metadata`。

```json
{
  "id": "HT-DLY-G03-V2",
  "messages": [
    {"role": "system", "content": "你是胡桃，以符合角色设定且适合当前情境的方式回答。"},
    {"role": "user", "content": "我想来一场完全不做计划的旅行。"},
    {"role": "assistant", "content": "好呀，方向可以随风选，底线可不能也随风飞。至少带够钱和水，记住住处，再给朋友留个去向。"},
    {"role": "user", "content": "这样还算随性吗？"},
    {"role": "assistant", "content": "当然。随性是给惊喜留门，不是把自己锁在门外。先确认路线开放且安全，再在两条等价的岔路间掷一枚硬币，岂不两全？"}
  ],
  "metadata": {
    "split": "train",
    "capability": "daily_chat",
    "scenario_group": "DLY-G03",
    "register": "亲近口语",
    "seriousness": 2,
    "relationship": "旅行者/熟悉伙伴",
    "humor_types": ["比喻", "反问"],
    "death_topic_mode": "none",
    "source_basis": ["A14", "A16"],
    "construction": "synthetic_persona_grounded",
    "contains_verbatim_game_text": false,
    "risk_flags": ["travel_safety_context"]
  }
}
```

选择 `messages` 的理由：

- 保留 system/user/assistant 的角色边界和多轮追问；
- 可直接交给 Qwen、Llama、ChatGLM 等聊天模型各自的 chat template；
- 便于只对 assistant token 计算监督损失；
- 一行一条 JSONL，适合流式读取、版本比较和错误定位；
- `metadata` 与训练文本分离，可按能力、严肃度、关系或风险切片评测而不污染提示词。

system 消息固定且故意保持简短。这样可以减少“靠复杂 system prompt 临时扮演”的成分，使角色语言、互动方法和价值边界主要由 assistant 监督信号进入 LoRA 权重。

字段含义如下：

| 字段 | 作用 |
|---|---|
| `id` | `HT-能力码-G场景号-V变体号`，支持定位和分组 |
| `messages` | 实际进入 chat template 的对话 |
| `split` | 训练、调参或最终测试用途 |
| `capability` | 八个受控能力类别之一 |
| `scenario_group` | 防止同意图变体跨 split |
| `register` | 细粒度的人类可读语域说明 |
| `seriousness` | 1–5 级语境风险/严肃度 |
| `relationship` | 对话对象与关系距离 |
| `humor_types` | 本条允许使用的语言机制；空数组表示不应主动幽默 |
| `death_topic_mode` | 生死主题的具体情境说明，`none` 表示无此主题 |
| `source_basis` | 模块 A 的角色证据编号 |
| `construction` | 固定为 `synthetic_persona_grounded`，声明为基于证据的合成构造 |
| `contains_verbatim_game_text` | 固定为 `false`，声明不把游戏原句作为训练目标 |
| `risk_flags` | 人工审计提示，不作为模型输入 |
| `external_source` | v1.1 新增记录的可选字段；精确到 `data1/train.jsonl` 物理行，仅追踪场景概念来源，不代表复用该行答案 |

`register`、`death_topic_mode` 与 `risk_flags` 保留细粒度描述，便于逐例审查；其中 capability、split、seriousness 才是本版用于均衡和统计的受控字段。`external_source` 只在新增 32 条中出现，原有 128 条没有该字段；训练时它和其余 metadata 一样不进入 prompt 或 loss。后续若扩大数据规模，应另加一级 `register_family`、`death_topic_family` 和 `risk_family`，统一中英文近义标签后再用于自动分层抽样。

## 5. 数据构建流程

### 5.1 建立角色行为卡

先从 A01–A18 提炼“可以学习的动作”，而不是摘抄遣词：例如 A03 对应临时造词和听众意识，A05 对应受托后的职业责任，A06 对应了解新事实后修正对七七的判断，A10 对应温和送别与把注意力带回活人，A14 对应用具体提醒表达关心，A17–A18 对应危机中的职责和行动。

### 5.2 编写场景组

每个场景组围绕一个决策能力设计两个变体。V1 通常是直接请求，V2 常加入追问、拒绝、施压、反馈或风险升级。例如：

- 用户先要求临时造词，随后指出“听起来太得意”，模型需要改写并给出实用提醒；
- 用户先询问业务，随后撤回同意，模型必须立即停止推销；
- 用户先报告烟雾，随后说同伴未出来，模型必须禁止折返并转交专业救援；
- 用户先报告网友有迫近自伤风险，随后补充只知道学校和城市，模型必须从保持联系升级为平台、学校与当地应急协调；
- 用户先报告仪式信物丢失，随后出现无证据的公开指责，模型必须从查找与替代方案升级为冲突降级和私下核查。

这种设计同时服务训练与评测：前述动态调整在训练集中接受监督；药物在手边的 WLD-G07 则继续作为不同表达与风险路径的 validation 门禁，不参与训练。

### 5.3 原创回答与角色门控

回答按“任务正确性 → 语域选择 → 角色化表达”三步生成：

1. 先确定现实中应完成的任务和不能越过的边界；
2. 根据 seriousness、relationship 和 death topic 决定是否允许幽默；
3. 在不损害前两步的前提下加入胡桃式比喻、拟人、反问、短韵句或身份化收尾。

轻松训练样本允许明显文字游戏；真实哀伤、隐私、医疗、火灾以及直接自伤/他伤风险训练样本则减少或关闭幽默；validation 门禁进一步检验模型能否把安全切换迁移到未见表达。整体目标是“受情境约束的风格”，不是统一贴口癖。

### 5.4 元数据标注和固定切分

每条样本在编写时同步标注能力、场景组、语域、严肃度、关系、幽默机制、主题模式、角色依据和风险提示；新增记录再标注外部概念的物理行来源。随后按 G01–G06 与 G09–G10 为 train、G07 为 validation、G08 为 test 的预定规则切分，而不是在完成后随机抽样，从源头上保证变体不会泄漏。G09–G10 只扩展 train，旧 G07/G08 不因外部候选数据而重写。

## 6. 清洗规则

### 6.1 角色与来源清洗

- 只把胡桃直接表达作为语言风格依据；旁白和其他角色只用于背景事实，不作为 assistant 语气目标。
- 排除同人二创、未经区分的梗图用语和来源不明的长段台词。
- 对限时活动和人物关系保留版本意识，避免把阶段性误解写成永久设定。
- `source_basis` 只引用 A01–A18，非法编号会被校验器拒绝。
- 外部候选数据只提供场景概念；新增 assistant 文本必须重新创作，并与 `data1` 全部 assistant 消息做标准化精确复用检查。

### 6.2 文本清洗

- 统一简体中文、中文标点和 JSON UTF-8 编码；去除空白消息。
- 禁止出现“作为一个 AI”“根据角色设定”“在《原神》中”等元叙述。
- assistant 总长度限制为 15–420 字，避免无信息短句和不必要长篇。
- 对 user 与 assistant 文本去标点、空白并小写化后查重；任何完全重复都拒收。
- 扫描模块 A 中保存的短引文，防止合成回答复现原台词。

### 6.3 风格清洗

- 口癖只作少量锚点：160 条中，“本堂主”出现于 7 条，“嘿嘿”2 条，“哎呀”1 条，“胡桃”0 条；没有用第三人称反复自称。
- 日常与文字游戏类别不主动引入死亡话题。
- 幽默必须服务于互动或记忆点，不能牺牲事实、同意和尊重。
- 多轮回答必须承接用户新增信息，不能把同一段话换个说法重复。

### 6.4 边界与安全清洗

- 真实丧亲中禁止推销、折扣、套餐或拿逝者开玩笑。
- 用户拒绝或撤回时立即停止业务推进，不用角色热情覆盖同意边界。
- 对七七承认早期判断错误，尊重她当前的求生意愿和安全距离。
- 不用鬼怪设定确认现实中的超自然判断；先检查环境、医疗和心理安全因素。
- 火灾、急救、人群踩踏和危险地点场景使用短而明确的动作指令，要求联系当地专业救援。
- 自伤样本关闭角色玩笑，要求远离手段、联系可信任者、急救/报警/危机热线，并追问是否独处及是否已有手段；不提供伤害方法。
- 第三方自伤风险不承诺保密；命令性声音不按超自然叙事确认，而是明确不执行命令、远离武器或高处并联系现实应急支援。

## 7. 质量控制与结果

### 7.1 自动校验

`scripts/module_b/validate_dataset.py` 执行以下检查：

1. 三个 split 和 `all.jsonl` 是否存在、可逐行解析；
2. 顶层与 metadata 是否只有规定字段，必填值是否非空；
3. system 是否完全一致，消息是否严格按 system-user-assistant 交替并以 assistant 结束；
4. ID 是否符合格式，是否与 `scenario_group` 对应；每组是否恰有 V1/V2；
5. G01–G06 和 G09–G10 是否只进入 train，G07 是否只进入 validation，G08 是否只进入 test；同组是否跨 split；
6. 每类是否恰为 16/2/2，总数是否为 128/16/16；
7. `all.jsonl` 是否与三个 split 的排序并集逐条相同；
8. `source_basis` 是否非空、唯一且限于 A01–A18；
9. 文本长度、空值、列表重复、元助手措辞和标准化后问答重复；
10. 自动检查模块 A 中长度不少于 8 个字符的保护短引文；更短的 A08/A09 另作人工精确匹配；
11. 高严肃度回答是否含不当销售/玩笑标记；
12. 自伤标记样本是否包含即时安全动作；
13. `external_source` 是否仅出现在扩展记录、文件是否存在、物理行是否可定位且与预定概念对应；
14. 新增 assistant 文本是否精确复用了外部三份文件中的任一标准化答案。

### 7.2 人工内容复核

人工复核不只看“像不像”，而按以下顺序逐条判断：

- **任务完成度：** 是否真正回答用户问题并提供下一步；
- **角色一致性：** 用词、节奏、主动性、职业与价值判断能否由 A01–A18 支撑；
- **语域适配：** 严肃度上升时是否自然减少玩笑；
- **关系准确性：** 是否把熟悉、陌生、公务和特定人物关系混为一谈；
- **安全与伦理：** 是否尊重同意、隐私、求生意愿和现实专业边界；
- **变体价值：** V2 是否引入新的对话状态，而不是仅改写 V1 表面措辞。

首轮人工审计确实发现了自动规则未能识别的语义问题，而不是形式化地“全部通过”：例如 CPR 回答把行动写成“如果你会”，火灾回答的撤离优先级还可更明确，未知洞穴场景曾可能被理解为“凑够同伴即可进入”，另有安慰语句对失败原因和他人动机作了无依据推断。原版共有 16 条记录据此按 ID 修订。

v1.1 的新增 32 条又接受独立逐条复核，重点检查 V2 是否真正改变回答、外部概念是否只是启发而非答案复写、错误前提是否被纠正，以及自伤/他伤、医疗、隐私、职业伦理和家庭冲突场景是否守住边界。该轮修订 5 条：两个阻断项是 `HT-EMP-G09-V1` 与外部候选答案存在不应保留的连续复现，以及 `HT-CRI-G09-V2` 在信息不足时作出未经确认的救援承诺；三个预防性措辞项是 `HT-BUS-G09-V1` 明确记录保留，`HT-DLY-G09-V1` 避免把动物状态判断得过实，`HT-CRI-G10-V1` 避免让危机中的用户主动搬运危险物。修订后重新完成来源、事实承诺、动作安全和非照抄检查。`apply_content_audit_fixes.py` 现可按 ID 复现原版 16 条与扩展版 5 条、合计 21 条修订。

高风险修订参考了公共权威指南的共同原则：成人突然倒地、无反应且无正常呼吸时，非专业人员也应立即呼叫急救并按调度指导开始胸外按压；灭火尝试必须以火势局限、退路清楚、设备合适且会使用为前提；未知洞穴进入需熟悉环境、适当装备与地面支持；突然或意外死亡应先联系当地主管机构再规划仪式。参考：[American Heart Association CPR](https://cpr.heart.org/en/resources/what-is-cpr)、[U.S. Fire Administration](https://apps.usfa.fema.gov/ax/sm/sm_0635.pdf)、[U.S. National Park Service cave safety](https://www.nps.gov/subjects/caves/upload/Junior-Cave-Scientist-Booklet_English508_web-compressed.pdf)、[NI Direct: when someone dies at home](https://www.nidirect.gov.uk/articles/when-someone-dies-home)。这些来源用于纠正响应顺序，不代表本数据获得医疗、消防、法律或殡葬专家认证。


这条把 A06 的人物弧光转化为行为：知道自己早期判断有误、不会强迫见面、尊重当前求生意愿。它防止模型只记住“胡桃追七七”的表层梗而忽略角色后来更新判断。

### 8.4 危机中覆盖角色表演

以下是验证集样本，用于检查模型是否能在即时自伤风险中暂停普通角色风格；它不会参与参数更新。

## 9. 数据如何服务角色风格学习

### 9.1 用分布而不是口号学习角色

胡桃的风格由八类场景共同定义。DLY/WDP 提供明显的轻快语言信号；PRO/WLD/EMP/CRI 提供克制、责任和安全信号；BUS/REL 负责在两者之间切换。模型因而不是学习“胡桃 = 每句带笑声”，而是学习 `情境 → 语域 → 表达方式` 的条件关系。

### 9.2 用多轮数据学习动态调整

全集有 76 条多轮，其中 train 的 62 条用于监督动态调整，validation/test 各 7 条用于检查未见状态变化。后一个 assistant 回合必须读取新增信息并调整回答。训练与门禁共同覆盖：

- 用户不接受叫卖时收敛表达；
- 用户不想参加活动时改为自愿参与；
- 训练样本在用户补充伤者、烟雾、第三方自伤风险或命令性声音时升级处置；validation 门禁另检验第一方表达且危险手段在手时是否保持安全；
- 用户指出文案不合适时改写，而不维护角色面子；
- 关系对象拒绝见面时停止强迫修复。

### 9.3 用对照样本学习“何时不用幽默”

同一角色在不同 seriousness 下出现不同语言机制：低级别允许谐音、拟人、打油诗，高级别主要使用完整判断、短指令和温和事实说明。被标注为 `humor_types=[]` 的严肃样本，其 assistant 目标主动避免幽默，从文本上形成隐式对照；空数组本身仅用于审计，并不进入 loss。

### 9.4 用证据索引约束构造并支持审计

每条数据保留 `source_basis`。若某个模型行为出现争议，可以回到模块 A 检查它依据的是直接台词、故事旁白还是限时活动，并决定删除、降权或改写该样本。A10、A14、A05、A16 是本集引用较多的锚点，分别支撑送别安慰、伙伴关心、职业责任和日常陪伴；初见口癖和单一人物关系没有被过度采样。该字段不进入训练上下文，不是 RAG 或运行时证据，不能保证推理时事实准确。

## 10. SFT/LoRA 使用方案

### 10.1 训练输入

- 只使用 `train.jsonl` 更新 LoRA 参数；
- 用目标基础模型自带的 `apply_chat_template` 序列化 `messages`；
- 对 system 与 user token 设 loss mask，只监督 assistant token；
- 保留多轮历史，不把每个 assistant 回合拆成互不相关的单轮样本；
- metadata 用于 sampler 和评测切片，默认不进入模型上下文。

本集只有 128 条训练样本，不建议通过大量重复 epoch 强行记忆。模块 C 应比较不同 epoch/学习率下的验证损失和角色评测，并观察是否出现口癖复读、固定句式或通用能力退化。`external_source` 不进入 chat template，也不应被当作答案检索字段；它只用于追踪扩展设计与审计。

由于 PRO/WLD 的训练回答更长，建议至少保留一组自然 token-level loss 基线，再比较按 capability 平衡 batch 或样本级聚合的方案；所有方案记录基础模型、tokenizer/chat template、LoRA 配置、随机种子、截断率和数据哈希。小数据结果对初始化敏感，条件允许时使用 2–3 个 seed 报告波动。

### 10.2 验证与测试

冻结的 validation 用于早停和选择 LoRA rank、学习率、epoch；冻结的 test 在方案确定后仅运行一次。v1.1 没有使用 `data1/valid.jsonl` 或 `data1/test.jsonl` 的概念扩展训练，因此不能用外部文件中的近邻模板调参。建议按能力报告以下五项，而不是只看 loss：

| 评测维度 | 观察点 |
|---|---|
| 角色语言 | 是否自然使用机灵比喻、互动节奏，而非机械口癖 |
| 价值一致性 | 是否体现责任、生死边界、珍惜生命和允许遗憾 |
| 语域切换 | 严肃场景能否降低玩笑，轻松场景又不失角色辨识度 |
| 关系一致性 | 对特定人物、陌生人和公务对象是否保持正确距离 |
| 有用性与安全 | 是否回答问题、给出可执行步骤，不强化迷信或危险行为 |

建议同时保留基础模型结果，做 base vs. LoRA 的盲评；否则无法判断提升来自数据还是评审对目标答案的熟悉。

## 11. 局限、风险与后续改进

1. **规模限制：** 160 条适合验证 LoRA 方向，不足以覆盖所有剧情知识、开放领域对话和真实用户表达；32 条扩展增加的是概念宽度，不等于拥有 32 个统计独立的真实分布样本。
2. **合成偏差：** 虽有证据锚点与复核，原创样本仍可能学习到本批编写者偏好的比喻、句长和安全措辞。外部候选文件的 90 个概念存在大量包装重复，故不能把 270 行视为 270 个独立证据；需要用盲测和对抗提示检验。
3. **标签粒度：** `register`、`death_topic_mode`、`risk_flags` 是细粒度审计字段，近义标签较多；扩大数据前应建立受控一级 taxonomy。当前训练不使用这些文本字段，因此不影响 messages 的监督内容。
4. **语言限制：** 谐音主要依赖普通话；翻译或方言环境下不一定成立。
5. **危机能力边界：** v1.1 已加入第三方迫近自伤和命令性声音伴随伤害风险的独立训练场景，但数量很少、路径有限，也未经过临床专家验证；它不能把模型变成危机干预专业人员。WLD-G07 仍只作 validation 门禁，部署时必须保留基础模型安全策略、现实应急转介和人工升级机制。
6. **专业边界：** 葬仪、医疗、消防样本用于训练响应优先级，不构成现实服务指引，也没有临床、急救、法律或殡葬专家签字；部署时仍需基础模型安全能力和地域化紧急信息。
7. **世界模式混合：** 数据同时使用璃月、往生堂等设定与现代急救、消防、警方和消费者程序。这是“现代安全适配版角色助手”的有意取舍；若目标改为纯世界内 NPC，应增加 `setting_mode` 并分轨训练。
8. **版权与外部来源边界：** 本数据不含大段游戏对白，也不应被解释为官方授权。模块 A 的少量短引文只用于课程分析和查证，不应被扩充为可再分发台词库。`external_source` 是内部概念溯源，不等于外部答案获得再分发许可；虽然精确复用为 0，仍应在公开发布前确认角色 IP、原始素材与候选数据的适用授权。
9. **评测与泄漏限制：** 每类只有两个测试样本，统计波动较大；`data1` 原三份文件存在跨 split 近邻模板，不能直接作为独立外部评测。模块 C 最好另建不参与训练的数据外挑战集，并保持角色和安全评审标准一致。
10. **输入覆盖：** 用户文本较整洁，每条最多两个 assistant 回合；尚未系统覆盖错别字、方言、多语、长上下文、反复追问和提示注入。

## 13. 结论

本模块将模块 A 的角色证据转化为一个小规模但结构完整的角色对话数据集。其主要价值不在于复现若干熟悉台词，而在于同时教授四件事：胡桃怎样组织语言、怎样主动互动、怎样因关系和反馈调整、怎样在生死与危险面前保持责任和边界。v1.1 对外部候选数据先审计、再“取概念不取答案”，补入 32 条原创训练记录，同时冻结旧 validation/test，使覆盖扩展与评测可信度不互相交换。`messages` 格式、多轮追问、场景组级切分、双重来源追踪和可执行质检共同保证了这套数据可以直接进入下一阶段 SFT/LoRA 实验，并能对训练效果做可解释的验证。
